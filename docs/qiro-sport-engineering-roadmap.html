01   Engineering Adjustments to PRD Roadmap

The PRD roadmap is structurally sound. The phase order — Foundation → Sports → Dice → Virtual Football → Horse Racing → Admin → QA — is the correct sequence. However, three adjustments are made from a pure engineering standpoint. These are not preference changes; they prevent concrete, known failure modes.

ADJUSTMENT 1

WebSocket gateway scaffolded in Phase 0, not Phase 3

The PRD defers real-time infrastructure to Phase 3 (Virtual Football). Retrofitting Socket.IO into an already-built NestJS + Next.js application mid-project causes restructuring across auth guards, module imports, and the client state layer. The WebSocket gateway must be wired as infrastructure in Phase 0 — even if zero events fire — at a cost of one day, saving three days of untangling in Phase 3.

ADJUSTMENT 2

Withdrawal management interface delivered in Phase 0, not Phase 5

The moment real users deposit money in Phase 0, withdrawal requests will arrive. If the operator has no interface to action them, funds are stuck and users lose trust immediately. At minimum, a withdrawal queue view (list + approve/reject + notes) must exist by end of Phase 0. The full admin dashboard — users, financials, game config, risk alerts — remains Phase 5.

ADJUSTMENT 3

Game engine math written and unit-tested before Phase 3 begins

The Poisson scorer (Virtual Football), weighted finishing order (Horse Racing), and Dice payout formula live in packages/game-engine and must be proven correct in isolation before the scheduler wiring begins. If math bugs surface inside a running scheduler, debugging is three times harder. This is a half-day of focused work that protects three weeks of Phase 3 build confidence.

Everything else is kept as-is Stack choices, phase ordering, database approach, third-party services, and timing estimates all stand as specified in the original roadmap.
02   Monorepo Architecture & Project Structure

The project uses a Turborepo monorepo with pnpm workspaces. This keeps shared types, the game engine, and the Prisma client in sync across all apps without duplication, and enables a single CI pipeline to lint, typecheck, and test everything together.

qiro-sport/
├── apps/
│   ├── web/              # Next.js 15 — player-facing PWA (mobile-first)
│   ├── admin/            # Next.js 15 — back office dashboard (operator only)
│   └── api/              # NestJS — REST API + WebSocket gateway + BullMQ workers
│
├── packages/
│   ├── db/               # Prisma schema, migrations, generated client
│   ├── types/            # Shared TypeScript interfaces (User, Bet, Round, etc.)
│   ├── game-engine/      # RNG logic, payout calculators, Poisson scorer — fully tested
│   └── ui/               # Shared Shadcn/Tailwind component base (used by web + admin)
│
├── turbo.json
├── pnpm-workspace.yaml
├── .github/workflows/ci.yml
└── package.json

Key Monorepo Rules

  • packages/db owns the Prisma schema exclusively. No other package writes migrations.
  • packages/game-engine has zero runtime dependencies on NestJS or Next.js. It is pure TypeScript with no side effects — importable and testable anywhere.
  • apps/admin deploys to a separate subdomain (admin.qirosport.com). It is never bundled into the player app.
  • Turbo pipeline: build depends on db#generate so the Prisma client is always fresh before building the API or either web app.
  • All environment secrets are split: apps/api/.env for backend secrets, apps/web/.env.local for public Next.js vars prefixed NEXT_PUBLIC_.

05   Database Schema
Critical Financial Rule All monetary values are stored as integers in kobo (1 NGN = 100 kobo). Never store Naira as a float. All payout calculations use integer arithmetic with floor rounding. This is non-negotiable.
Immutable Ledger Rule The transactions table must never have UPDATE or DELETE operations. Every wallet change — deposit, stake, win, refund — is a new append-only row. Wallet balance is the authoritative running balance on the latest transaction row.

06   System Architecture Overview

6.1 Request Flow

    │

    │    (auth, bets, wallet, odds)              │

    └─── WebSocket connection ───────────────────┤     All persistent data

                                                │
                                    ┌───────────┼───────────┐
                                    │           │           │
                               VF League A  VF League B  Horse Racing
                               (every 4m)  (every 4m,   (every 3m)
                                           offset 2m)
                                    │
                               Odds Poller
                               (every 5m — TheOddsAPI)
                                    │

                               (polls scores, settles bets)
                                    │
                               Reconciliation Cron
                               (hourly — wallet integrity check)

6.2 WebSocket Event Architecture

Clients subscribe to rooms on connection. The server pushes events; the client never polls for game state. This is critical for the 4-minute and 3-minute game cycles where many users need simultaneous updates.

RoomEvents PublishedSubscribers
vf:league-aupcoming, betting_open, halfTime, result, standingsAll users on Virtual Football tab, League A
vf:league-bupcoming, betting_open, halfTime, result, standingsAll users on Virtual Football tab, League B
horse-racingrace_card, betting_open, in_progress, resultAll users on Horse Racing tab
user:[userId]balance_updated, bet_settled, withdrawal_statusSingle user's private channel

6.3 Virtual Game Cycle — State Machine

UPCOMING ──(T-90s)──► BETTING_OPEN ──(T-15s)──► BETTING_CLOSED
                                                       │
                                          RNG seed committed + result generated
                                          (result held — not revealed yet)
                                                       │
                                               IN_PROGRESS
                                          (VF: half-time reveal at +30s)
                                          (HR: "race in progress" 30s delay)
                                                       │
                                                  SETTLED
                                          (all bets settled, wallets credited,
                                           seed revealed, next round published)
Scheduler Resilience On API startup, the scheduler must query for any rounds stuck in BETTING_OPEN, BETTING_CLOSED, or IN_PROGRESS state and either resume them or mark them VOID with full refunds. A crashed server mid-cycle must not leave user funds in limbo.

6.4 Wallet Mutation Safety

-- Every wallet debit/credit follows this pattern inside a DB transaction:

BEGIN;
  SELECT * FROM wallets WHERE user_id = $userId FOR UPDATE;
  -- ↑ Row-level lock. Prevents concurrent mutations on the same wallet.

  INSERT INTO transactions (wallet_id, type, amount_kobo, running_balance_kobo, ref)
  VALUES ($walletId, 'STAKE', $amount, $newBalance, $ref);

  UPDATE wallets SET balance_kobo = $newBalance, updated_at = now()
  WHERE user_id = $userId;
COMMIT;

PHASE 4

Virtual Horse Racing

2 Weeks

Backend + Game Engine

  • packages/game-engine: weighted random shuffle for finishing order (Fisher-Yates with weights)
  • Seed 48 named horses with jockey and base_rating into DB
  • Win odds calculation: (horse_rating / sum_of_all_ratings) × house_margin
  • HorseRacingScheduler: BullMQ repeating job, 3-min cycle
  • Draw 8 horses per race (weighted by current_rating for realistic selection)

08   Risks & Engineering Mitigations
RiskLikelihoodImpactEngineering Mitigation
Race condition: two concurrent bets deplete wallet below zero Medium Critical SELECT FOR UPDATE on wallet row inside every debit transaction. CHECK constraint (balance_kobo >= 0) as DB-level safety net.
Double deposit from Paystack webhook firing twice High Critical Unique constraint on transactions.ref. First webhook inserts; second webhook hits unique violation and returns 200 silently.
Paystack declines gambling merchant account High Critical Register as "entertainment/fintech." Flutterwave account provisioned as drop-in fallback. Architecture uses a payment provider abstraction layer so switching requires minimal code changes.
Virtual game scheduler crashes mid-cycle — user funds in limbo Medium High On API startup, query for rounds in non-terminal state. Rounds in BETTING_OPEN → void + refund. Rounds in IN_PROGRESS → continue to settlement. BullMQ job history enables replay.
Wallet balance discrepancy due to application bug Low Critical Hourly BullMQ cron compares sum(transactions) vs wallet.balance_kobo for all wallets. Any mismatch fires a Sentry alert immediately.
RNG disputed by users (fairness claims) Medium High Provably fair: SHA256(server_seed + round_id) committed to DB before round starts. Seed revealed after settlement. Users can independently verify any historical round.
TheOddsAPI outage during live fixtures Low Medium Cache odds with 5-min TTL; serve stale cache up to 2h before kickoff. If cache is older than 2h at kickoff, suspend new bet placement and alert operator. Settlement still runs from scores feed.
Float rounding errors on payout calculations Medium High All amounts stored and calculated in kobo (integers). All multiplications done in integer arithmetic. Payouts always floor-rounded — never round up in user's favour on the platform side.
User fraud — chargeback abuse Medium Medium Withdrawal delay (same-day / next-day). Minimum KYC (bank account verification) on first withdrawal. Unusual deposit pattern flagging (10+ in short window). Withdrawal amount capped without KYC.
Regulatory action from LSLGA or state bodies Low (at scale) High Soft launch without mass advertising. Begin URC state license application once platform is profitable. Avoid SEO-aggressive content targeting gambling keywords initially.

9.5 Key Engineering Conventions

  • Money is always kobo. Any function that accepts or returns money must have kobo in its parameter/return type name. No ambiguity.
  • All DB writes through Prisma transactions. No raw SQL for mutations. No Prisma outside apps/api.
  • Virtual game engine has no NestJS imports. It stays a pure TypeScript library. This enables testing without spinning up the full app.
  • WebSocket auth. Clients authenticate the Socket.IO connection by sending their JWT in the handshake headers. The gateway validates the token on connection.
  • No floating-point arithmetic on money. All payout calculations: Math.floor(stake_kobo * odds_decimal) where odds is also a rational number.
  • Paystack webhook validation is non-negotiable. Every webhook endpoint must validate the X-Paystack-Signature header before processing. No exceptions.
